# KW66 Lab v3.8 — Morse Messenger prototype

## Новый этап: KW66 как скрытая Morse-клавиатура

В v3.8 добавлен первый прототип **Morse Messenger** поверх уже подтверждённых событий KW66:

- `D1 09` — Previous → `.`
- `D1 07` — Play/Pause → `-`
- `D1 08` — Next → завершить букву
- отдельная команда «Пробел» в лаборатории — временно для тестирования

Приложение по умолчанию не показывает введённый Morse или текст сообщения. Текст существует только в памяти и на этапе отправки сразу передаётся в криптографический слой.

### Криптографический прототип

v0.1 использует Web Crypto API: AES-256-GCM для шифрования локального payload. Кнопка «Отправить» пока делает **только локальный crypto-loopback** (encrypt → decrypt), а не притворяется реальной сетевой отправкой. Это сознательная граница первого этапа.

Pairing-код пока только создаёт стабильный отпечаток приглашения и подготавливает слой. Настоящий защищённый канал между двумя телефонами будет следующим этапом; для него потребуется транспорт/signaling и аутентифицированный обмен ключами.

## План реализации

1. Доказать Morse-ввод через реальные `D1 07/08/09`.
2. Добавить настоящий pairing двух устройств.
3. Добавить E2E session keys и replay protection.
4. Добавить транспорт между двумя телефонами.
5. Полученный plaintext отправлять только на `C5` → KW66.
6. Сделать Android background companion, чтобы канал работал при погашенном экране.
7. Убрать даже локальное хранение plaintext после доставки.

## Важное ограничение

PWA отлично подходит для BLE и криптографического прототипа, но для постоянной фоновой работы Android нужен нативный companion/service.

# KW66 Lab v3.3

## Что нового в v3.3 (исправление по фидбеку с реального железа)

- **0xC5 (текст на часы) — найден пропущенный заголовок.** В v3.2 первый байт
  реального текста ошибочно уходил как часть служебных полей. Формат первого
  куска на самом деле: `C5 00 <id:1б> <len:1б, длина текста в байтах> <текст…>`.
  Без этого: терялся первый символ, и часы показывали не ту иконку. `len`
  теперь считается автоматически.
- **id=0x00 — это категория "входящий звонок"**, подтверждено на реальном
  устройстве (экран вызова, кнопка сброса гасит экран) — совпадает с
  единственным таким случаем в исходном логе. По умолчанию шлём id=0x01;
  значения остальных id (кроме того что "не 0") пока не расшифрованы —
  в логе видел 0x02/0x04/0x09/0x13/0x15, все давали обычную иконку.

## Что нового в v3.2

- **Разобран btsnoop конкретной сессии** (не только код парсера — реальный разбор лога).
  Уточнение: в снупе оказалось много ACL-соединений с разными устройствами телефона;
  профиль GloryFit (0x55FF) был только в одном conn_handle — если будешь сверять
  свои дальнейшие логи руками, **сначала фильтруй по conn_handle**, иначе handle
  16/21/28 и т.п. могут случайно совпасть с другим BLE-устройством из того же снупа.
- **Опкод 0xC5 расшифрован — произвольный текст на экран часов.** Телефон режет
  UTF-16BE строку на куски по ≤18 байт: `C5 <seq> …`, часы квитируют каждый кусок
  `C5 <seq>`, конец — `C5 FD` (от телефона) / `C5 FD <статус>` (от часов). В снупе
  пойман тестовый пуш `"Заголовок уведомления: Notification content:"` — то есть это
  общий канал показа уведомлений, не привязанный к конкретному приложению-источнику.
  Реализовано в разделе 6b — **не проверено на реальных часах**, только на основе
  анализа лога.
- **Опкод 0xA1 — чтение серийника/модели** (ASCII-строка, в снупе пришло
  `RH192PDV003129`).
- Исправлена опечатка в находке про кастомный 128-бит сервис ниже (было
  `0x00006287`, реальный UUID — `12a24d2e-fe14-488e-93d2-173c8762-0000` и
  соседний `…-8763-0000`; байты в старой заметке были просто переставлены).
  Трафика на этих characteristic'ах за сессию не было — только обнаружение.
- **Акселерометра/жеста "поднять руку" в BLE-трафике НЕТ** (см. находку №5 ниже —
  подтверждено повторно на реальном логе: единственный высокочастотный notify —
  это фон 0xA2 (константа `A2 64`, ~1 раз/сек, похоже на keepalive), плюс уже
  известные HR/шаги. Жест обрабатывается прошивкой часов локально по сырым данным
  акселерометра; по BLE передаётся только команда включить/выключить саму функцию
  (в логе это, вероятно, один из вариантов 0xD7 — см. ниже), а не поток координат.
  Чтобы точно поймать эту команду, нужен **изолированный снуп**: включить лог,
  переключить ТОЛЬКО тумблер "поднять руку — включить экран" в GloryFit (без HR-теста,
  без открытия других экранов), выключить лог — тогда diff покажет ровно один
  новый TX-пакет.

## Что нового в v3.1 (влито из параллельной ветки разбора протокола)

- **F7 — 11 байт, не 9.** Последние 2 байта — min/max пульса (подтверждено живым значением характеристики в nRF Connect). Раньше эти 2 байта отваливались и засоряли буфер лишним мусором.
- **E5 больше не фиксированной длины.** Он бывает 2 байта (`E5 11` — просто отметка «идёт измерение», без значения) и 4 байта (`E5 11 00 XX` — реальный пульс). Буферизация теперь резюмируется по следующему известному opcode + короткий debounce-таймер (25 мс), вместо склейки в один пакет и последующего «пропуска HR» — то есть находка №3 ниже (артефакт `E5 11 A2 64`) в v3.1 **не должна больше возникать** сама по себе: оба пакета разбираются раздельно и корректно.
- Восстановлена ветка `writeValueWithoutResponse` в `send()` — нужна для характеристик без обычного `write` (например `34F1` на BLE5).
- Добавлено пассивное прослушивание `0xFEE7`/`0xFEA1` (Tencent/WeRun UUID, отдельный неисследованный канал) — вдруг само что-то придёт. Трафик с него в лог идёт как сырой hex, без попытки трактовать по семантике A2/B2/E5/F7.

## Что нового в v3

- **Live-пульс**: график E5-потока (~1 Гц), статистика окна 5 мин.
- **Тест восстановления (перетрен)**: падение пульса за 60 с после нагрузки → вердикт.
- **Стресс-монитор v1**: HR>100 три минуты + шаги стоят → дыхательный экран 4-7-8 с живым пульсом.
- **Детектор «вруна»**: базовая линия 10 с → вопрос → измерение пиковой реакции.
- **Фаззер команд**: массовая отправка кандидатов (HR-старт / binding / вибрация) с авторазбором откликов.
  Периодика (A2/F7/B1) фильтруется — показывается только «интересное».
- **btsnoop-парсер**: загрузи `btsnoop_hci.log` (HCI snoop log Android) — парсер вытащит ATT-записи,
  соберёт handle→UUID и покажет уникальные команды, которые официальное приложение шлёт часам.
  Это главный инструмент поиска init-последовательности и команды старта HR.

## Важные протокольные находки (KW66)

1. `E5 00` с телефона **не стартует** замер пульса. Стрим `E5 11 00 XX` идёт только когда замер
   запущен на самих часах. Телефон — пассивный слушатель.
2. Терминатор пустой истории шагов — `B2 FD E0` (не только `B2 FD F5`, третий байт — что-то вроде чек-суммы/варианта, декодер проверяет только `b[1]===0xFD`).
3. ~~Артефакт фрагментации: `E5 11 A2 64`~~ — исправлено в v3.1 корректной буферизацией (см. выше), пакеты `E5 11` и `A2 64` теперь разбираются отдельно.
4. B1 (realtime steps, 18 байт): шаги предположительно в последних двух байтах BE.
5. Raw-акселерометра и сырого PPG по BLE нет — все фичи строятся на пульсе/шагах.
6. Полная карта GATT-профиля (nRF Connect): основной канал `0x55FF` (33F1/B003 write, 33F2 notify); `0x56FF` существует, но ни разу не присылал данных; `0x0000d0ff-...` — OTA/DFU загрузчик прошивки, не трогать; `0xFEE7` (FEA1/FEA2/FEC9, Tencent UUID) — не исследован, с v3.1 слушаем пассивно; `0x1812` HID — часы можно использовать как BLE-клавиатуру (потенциальный пульт для камеры/медиа); ещё один нетронутый канал — кастомный 128-бит сервис `12a24d2e-fe14-488e-93d2-173c????0000` с characteristic'ами `ffd0`/`8762`/`8763` (см. v3.2 выше).
7. `34F1` (BLE5) в реальном логе несёт большую бинарную передачу (опкод `0x27`, ~1500+ пакетов по ~240 байт за раз — похоже на загрузку кастомного циферблата/картинки, не прошивку — это отдельный сервис).

## Как снять btsnoop

Android: Настройки → Для разработчиков → «Bluetooth HCI snoop log» (вкл) → поработай с часами
через GloryFit (подключение + замер пульса + вибрация из приложения) → выключи лог.
Файл: `/sdcard/btsnoop_hci.log` или через `adb bugreport` (на новых Android snoop лежит внутри bugreport).
Загони файл в раздел 8 приложения.

- Добавлен **Motion Lab**: пассивный сбор всех RX-пакетов во время 30-секундного окна и отдельные экспериментальные кнопки C4 01/02/03 и D7 00/01/02.

- Опасные операции сброса/OTA в новый Protocol Lab намеренно не добавлялись.

## Что нового в v3.6

- **Motion Sniffer 60 с** заменяет прежний автоматический Correlator: во время эксперимента приложение **не отправляет никаких BLE-команд**.
- В эксперимент записывается **весь входящий RX**, включая обычную периодику вроде `A2 4B`; она больше не отбрасывается фильтром.
- Каждый RX-пакет сохраняется с миллисекундным timestamp, UUID характеристики, полным hex и ручной фазой эксперимента.
- Добавлены ручные маркеры **REST / MOVE / SHAKE**. Они не влияют на часы, а только помечают момент физического состояния в логе.
- Рекомендуемый протокол теста: примерно 15 с REST → 15 с MOVE → 15 с REST → 15 с SHAKE.
- Экспорт JSON теперь содержит полный RX-лог, распределение opcode и сводку по фазам.
- Во время Sniffer любые Protocol Lab TX-команды блокируются, чтобы не загрязнять эксперимент искусственным трафиком.
- `CB` и `31` по-прежнему считаются **неподтверждёнными RX-кандидатами** и никогда автоматически не отправляются.
- `C4` остаётся кандидатом camera/gesture, `D7` — кандидатом DND; они не считаются интерфейсом акселерометра.

### Интерпретация результата v3.6

Главный критерий: opcode должен появляться или заметно учащаться в фазах `MOVE`/`SHAKE` и отсутствовать либо быть существенно реже в `REST`.

Один только `A2 4B` доказательством движения не является: это периодический ответ батареи. `B1` также нельзя автоматически считать raw accelerometer — это realtime activity/steps-поток.

Следующий шаг после успешного теста — сравнить частоту и содержимое новых opcode по четырём фазам и отдельно проверить кандидатов `CB`, `31` и любые ранее неизвестные байты.
