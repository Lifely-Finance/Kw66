# KW66 Morse Messenger v4.0

Полный переход от лабораторного прототипа (v3.13, локальный crypto-loopback)
к рабочему сквозному шифрованному каналу между двумя часами KW66 через два
телефона. Все диагностические разделы предыдущей версии (HR/шаги, стресс,
детектор реакции, фаззер, btsnoop-парсер, Motion/Protocol Lab) убраны —
если понадобятся снова, они остались в архиве `KW66Lab-PWA-v3_13`.

## Как это работает

```
Часы A --Морзе(BLE D1)--> Телефон A --шифрование(AES-256-GCM)--> Supabase
                                                                     |
Часы B <--текст(BLE C5)-- Телефон B <--расшифровка----------------- +
```

- На экране телефона никогда не отображается ни введённый Морзе, ни текст
  сообщения (кроме специально свёрнутого режима отладки для калибровки
  без часов — по умолчанию выключен).
- Сервер (Supabase) видит только зашифрованные байты и момент отправки;
  строка с сообщением удаляется сразу после того, как получатель её забрал.

## Установка

### 1. Supabase
1. Создай бесплатный проект на supabase.com.
2. Открой SQL Editor, выполни целиком `supabase-schema.sql` из этого архива.
3. Скопируй `Project URL` и `anon public` ключ (Project Settings → API).

### 2. Хостинг PWA
Любой статический HTTPS-хостинг (GitHub Pages и т.п.) — Web Bluetooth и
Web Crypto требуют secure context. Залей все файлы этого архива как есть.

### 3. Pairing (один раз на пару устройств)
1. На обоих телефонах открой приложение → раздел «2. Защищённый канал» →
   вставь URL и anon key → «Сохранить».
2. На телефоне A: «Создать приглашение» → получишь код вида `K7F4-92MX-QP8L-3RTN`.
3. Передай этот код на телефон B любым способом (Telegram, голосом — не
   важно, это не тот канал, который защищает переписку).
4. На телефоне B: вставь код → «Подключиться по коду».
5. На обоих экранах появится одинаковый **fingerprint** (5 байт). Сверь
   его между устройствами один раз — это разовая защита от подмены ключа
   на стороне сервера. Дальше pairing переживает перезапуск приложения
   (ключи хранятся в IndexedDB на устройстве, приватный — как
   неизвлекаемый CryptoKey).

### 4. Использование
1. «Подключить часы» на каждом телефоне (Web Bluetooth к своим часам).
2. На часах в управлении плеером: Previous — точка (сразу, без задержки),
   Next — тире (сразу, без задержки), Play/Pause — команда серией тапов:
   1 тап фиксирует текущую букву и переходит к следующей (если буква уже
   зафиксирована — 1 тап это пробел), 2 тапа подряд — показать превью и
   поставить отправку в очередь (см. ниже), 3 тапа подряд — удалить
   (незавершённую букву целиком, а если стирать нечего — последнюю
   зафиксированную).
3. **Превью и автокоррекция перед отправкой (2 тапа Play).** Приложение
   прогоняет набранный текст через встроенный словарь RU/EN
   (`dict.js`) — чинит опечатки на расстоянии 1-2 буквы и раскрывает
   точные сокращения (СПС→СПАСИБО, U→YOU и т.д.) — и на несколько
   секунд показывает результат на ТВОИХ ЖЕ часах через `sendWatchText`.
   Если за это время ничего не нажать — сообщение уходит в исправленном
   виде. Если нажать любую кнопку — отправка отменяется, в буфер
   возвращается исходный (нескорректированный) текст для ручной правки.
   Отдельно от словаря, ещё на уровне самого Морзе: если введённый
   паттерн точек/тире не распознан, ищется ближайший валидный код
   (на 1 элемент отличается) — это работает всегда и тихо, без превью.
4. Получатель увидит обычное уведомление на своих часах — приложение
   ничего не покажет и не сохранит.
5. **Тест без второго телефона (временно):** в свёрнутом «Режиме отладки»
   раздела 3 есть кнопка «⚠ ВРЕМЕННО: показать как входящее» — она гонит
   набранный текст прямо на подключённые часы через `sendWatchText`,
   минуя шифрование и relay целиком. Полезно проверить ввод/отображение
   на одном устройстве, но это не тест реального канала — убрать кнопку
   перед использованием на два телефона.

## Архитектурные решения и их границы

- **Точка/тире — отдельные кнопки, а не одна с распознаванием по времени.**
  Настоящий hold-time недоступен (часы шлют одно BLE-событие на клик — см.
  диагностику сырым рекордером выше). Прежняя схема v4.4 (пауза ПЕРЕД тапом
  на одной кнопке) была структурально сломана: первый элемент любой буквы
  не с чем сравнить, поэтому он всегда классифицировался как точка — буквы,
  начинающиеся с тире (T, N, M, O, ...), нельзя было ввести с первого раза.
  Теперь Previous = точка, Next = тире — метафора «телеграфного ключа» с
  двумя плечами: каждый элемент срабатывает немедленно и независимо, без
  калибровки темпа и без риска «уехать». Play освобождён под управляющие
  команды (см. ниже) — 1/2/3 тапа подряд, тот же принцип, что раньше
  использовался только для Next (commit/space/send).
- **Play, а не Previous — теперь единственная кнопка с задержкой.** Три
  функции (зафиксировать/пробел, отправить, удалить) различаются числом
  тапов подряд в окне `BURST_WINDOW_MS`, поэтому приложение ждёт конца
  серии, прежде чем сработать. Previous/Next срабатывают мгновенно — это
  осознанный компромисс: элементы буквы вводятся быстро, а на команды можно
  позволить себе секунду задержки.
- **Словарь — статический файл, а не пользовательские данные.** `dict.js`
  содержит только зашитый в приложение список слов и таблицу точных
  сокращений — это код, а не переписка, поэтому его можно спокойно
  кэшировать service worker'ом наравне с остальным app shell'ом, не
  нарушая принцип «сообщения нигде не хранятся».
- **Почему превью — на часах, а не на телефоне.** Экран телефона
  принципиально ничего не показывает (см. концепцию выше), поэтому
  единственное место для обратной связи по автокоррекции — часы
  получателя-тебя-самого. Превью запускается только в момент отправки
  (2 тапа Play), а не при каждом слове — иначе пришлось бы гонять
  тексты на часы на каждый пробел, что и шумно, и лишний трафик BLE.
- **Отмена вместо подтверждения.** Не стали вводить отдельный жест
  «подтвердить отправку» — тайм-аут молчания сам подтверждает, а любой
  тап откатывает к исходному тексту. Это не требует новых кнопок и
  комбинаций, но означает, что случайный тап во время превью всегда
  трактуется как «я передумал», а не как часть следующего сообщения.
- **Простой Левенштейн, а не частотный словарь.** Коррекция слова —
  ближайшее по расстоянию редактирования слово из списка; при равном
  расстоянии до двух кандидатов побеждает тот, что раньше встретился в
  массиве `EN_WORDS`/`RU_WORDS`, а не тот, что вероятнее по смыслу или
  частоте. Для коротких сообщений это обычно незаметно, но не стоит
  ждать интеллектуального выбора при неоднозначных опечатках.
- **Буква фиксируется на каждый одиночный Play (1 тап), а не только перед
  пробелом.** В v4.0 `commit()` вызывался только внутри `space()`, поэтому любое слово
  длиннее одной буквы схлопывалось в один нераспознаваемый паттерн (`□`) —
  это и было причиной «неправильного и неполного» чтения Морзе.

- **ECDH P-256 вместо X25519.** Нативно поддерживается Web Crypto API во
  всех современных браузерах без сторонних библиотек — важно для офлайн-
  кэша PWA и минимизации поверхности атаки. Криптографическая стойкость
  для этой задачи эквивалентна.
- **Приватный ключ создаётся `extractable:false`** и хранится в IndexedDB
  как объект CryptoKey, а не как экспортированные байты — браузер не даёт
  прочитать его в чистом виде даже из JS-кода самого приложения.
- **Сессионный AES-ключ никогда не сохраняется** — пересчитывается заново
  из identity-пары при каждом запуске приложения.
- **Fingerprint нужно сверять руками один раз.** Это единственная защита
  от активной подмены публичного ключа на стороне Supabase — без неё
  сервер теоретически мог бы подсунуть свой ключ одной из сторон.
- **RLS в Supabase открыт (`true`) для anon-ключа.** Секретность канала
  держится на непредсказуемости кода приглашения (~80 бит) и на том, что
  содержимое всё равно зашифровано. Это осознанное упрощение для
  одиночного прототипа, а не модель доступа для множества пользователей.
- **Нет фонового режима.** Работает, пока PWA открыта на экране (Web
  Bluetooth это требует). Для работы при выключенном экране на Android
  нужен нативный компаньон-сервис (следующий этап, см. также заметку про
  `DeviceIntentService` у Imilab/GloryFit в файле памяти проекта).
